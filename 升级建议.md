优先级建议如下。

第一，增加 job store / history，让系统支持增量搜索。

现在如果系统每次运行都重新抓取、重新过滤、重新评估，就更像一次性脚本。升级后应该保存历史职位，识别哪些是新职位、哪些已经看过、哪些被拒绝、哪些已投递。

核心表结构可以是：

jobs
- id
- source
- source_url
- title
- company
- location
- description_hash
- first_seen_at
- last_seen_at
- status: new / seen / saved / rejected / applied / expired
- raw_description
- normalized_description

运行逻辑变成：

scrape jobs
→ normalize identity
→ deduplicate
→ compare with database
→ only assess new or changed jobs
→ update status

这一步非常关键，因为它让系统从“搜索工具”变成“持续监控 agent”。

第二，增加 decision trace，让每个职位的保留、过滤、评分都有结构化理由。

不要只输出分数。应该输出机器可读的判断依据，例如：

{
  "job_id": "abc123",
  "decision": "keep",
  "score": 82,
  "confidence": 0.78,
  "matched_skills": ["Python", "FastAPI", "RAG", "AWS"],
  "missing_skills": ["Kubernetes"],
  "seniority_signal": "junior-to-mid",
  "experience_requirement": "1-2 years",
  "location_signal": "Dublin hybrid",
  "risk_flags": ["mentions production ML experience"],
  "reason": "Strong match for applied AI backend role, but Kubernetes requirement may be a gap."
}

这会直接提升项目质量。面试官最容易质疑 LLM 项目：“为什么它这么判断？”decision trace 可以回答这个问题。

第三，增加 preference memory，让系统根据用户反馈调整排序。

你可以让用户对职位做简单反馈：

save
reject
not relevant
too senior
wrong location
wrong tech stack
not AI enough
already applied

然后生成用户偏好：

{
  "preferred_titles": ["AI Engineer", "Applied AI Engineer", "LLM Engineer"],
  "avoid_titles": ["Data Analyst", "Senior ML Engineer"],
  "preferred_skills": ["RAG", "FastAPI", "AWS", "LangGraph"],
  "avoid_keywords": ["5+ years", "PhD required", "onsite only"],
  "preferred_locations": ["Dublin", "Ireland", "Remote EU"]
}

这样下一轮 ranking 可以加入个性化权重：

final_score =
  cv_match_score * 0.60
+ preference_score * 0.25
+ freshness_score * 0.10
+ company/source_quality_score * 0.05

这一步会让系统更像 agent，而不是静态 filter。

第四，增加 planner / executor / reviewer 架构。

现在你的流程可以继续保留，但内部命名和职责可以更 agentic：

Planner:
- 根据 CV 和用户偏好生成搜索计划
- 决定 titles、locations、sources、keywords、search budget

Executor:
- 调用 job source 工具
- 抓取职位
- 标准化字段

Filter:
- 快速排除明显不相关职位
- 控制 LLM 成本

Assessor:
- 对候选职位做结构化评分

Reviewer:
- 检查评分结果是否一致
- 生成 daily summary / explainability report

Memory:
- 保存历史职位、用户反馈和偏好

这不一定需要一开始就上 LangGraph。你可以先用普通 Python class 实现清晰模块边界。重点是系统设计，而不是框架。

第五，增加 evaluation benchmark。

这是最有面试价值的一步。你可以准备一个小型人工标注集，例如：

100 条真实职位
每条职位标注：
- keep / reject
- ideal score: 1-5
- reject reason
- seniority label
- skill match label

然后评估：

filter precision
filter recall
false rejection rate
precision@10
NDCG@10
cost per useful job
average latency
noise reduction rate

其中最重要的是 false rejection rate。因为求职系统里，误删一个好职位比保留一个烂职位更严重。

你可以把 evaluation 写成：

Before:
996 jobs → 54 reviewed
Noise reduction: 94.6%

After:
Precision@10: xx
False rejection rate: xx
Average LLM cost per run: xx

即使数据集不大，也比没有评估强很多。

第六，增加 cost control。

这对 AI Engineer 项目很重要。你可以明确分三层处理：

Layer 1: cheap rule filter
- title relevance
- seniority
- location
- duplicate
- closed job
- obvious mismatch

Layer 2: lightweight model / embedding filter
- semantic relevance
- skill overlap
- job family similarity

Layer 3: expensive LLM assessment
- only top candidates enter

输出统计：

Scraped: 996
After rule filter: 210
After semantic filter: 92
After LLM assessment: 54
Estimated cost saved: xx%

这能证明你理解真实 LLM 系统不是“全部扔给 GPT”。

第七，增加 semantic layer，但不要把它做成完整 RAG。

JobRadar 不需要传统 RAG，但可以加入 embedding 用于职位相似度、去重、偏好学习和粗排。

适合加入的地方：

CV embedding vs JD embedding → semantic match score
job-to-job embedding → near-duplicate detection
saved jobs embedding → preference similarity
rejected jobs embedding → avoid-similarity penalty

例如：

semantic_score = cosine(CV_profile_embedding, job_description_embedding)
preference_score = cosine(saved_jobs_centroid, job_embedding)
reject_penalty = cosine(rejected_jobs_centroid, job_embedding)

这能把你的 rag_demo 能力迁移到 JobRadar，但不会强行把 JobRadar 做成 RAG。

第八，增加 source abstraction。

现在如果数据源是 JobSpy / Adzuna，后续可以抽象成统一接口：

class JobSourceConnector:
    def search(self, plan: SearchPlan) -> list[RawJob]:
        ...

然后支持：

AdzunaConnector
JobSpyConnector
GreenhouseConnector
LeverConnector
RemoteOKConnector
ManualCSVConnector

这样系统更容易扩展，也能规避“项目绑定某一个数据源”的问题。

第九，增加 application status tracking。

不建议做自动投递，但可以做状态管理：

new
reviewed
saved
applied
interviewing
rejected_by_company
closed
ignored

这能形成完整闭环：

job discovery → evaluation → user decision → application tracking → feedback → preference update

比单纯搜索职位更像产品。

第十，增加 reporting / analytics。

你可以生成一份 weekly report：

This week:
- 183 new jobs found
- 21 strong matches
- 8 saved
- 3 applied
- Most common required skills: AWS, FastAPI, LangChain, Docker
- Your biggest gaps: Kubernetes, production ML, CI/CD
- Best matching titles: Applied AI Engineer, Junior LLM Engineer

这对项目展示很有用，也符合你的求职场景。

最终推荐升级路线：

Phase 1: Core system quality
1. job store / history
2. decision trace
3. application status
4. daily / weekly summary

Phase 2: Agent intelligence
5. preference memory
6. planner / executor / reviewer split
7. semantic scoring
8. cost control

Phase 3: Engineering maturity
9. evaluation benchmark
10. source abstraction
11. observability / tracing
12. deployment packaging
